# 工作台视图的想法：Edit Mode、统一的导航语法、外部编辑器

日期：2026-10-04。用户提出的初步想法和主控的看法，**只是记录，没有拍板，也没有代码**。相关的已定原则见 [architecture.md](../architecture.md) §3.3（界面的分工），第一个专用视图是 `/preview`（[guide/preview.md](../guide/preview.md)）。

## 1. 用户的想法

### 1.1 目标

> 不是让 TUI 变成 IDE，而是让用户在 Agent 工作台里，永远不需要为了"小修改"逃出去。

痛点：人舍不得的不是 VS Code 本身，而是一套已经形成肌肉记忆的操作（快速跳转、搜索、改两行、看 diff、切文件），同时又希望 agent 的任务状态、历史、浏览器预览都在一个地方。

结论：内置轻量 Edit Mode，加 Vim 语法，加外部编辑器逃生口。不造 IDE，不造完整 Vim。把"编辑"降级成工作台的一个原语。

### 1.2 Edit Mode

- 平时是 agent 的界面。按一个键（如 `e`），当前选中的文件或 agent 正在处理的位置原地进入编辑状态；按 Esc Esc 回到工作台。
- Vim 键位是默认或可选的操作方式：`hjkl`、`w/b/e`、`gg/G`、`/`、`n/N`、`i/a/o`、`dd`、`yy/p`、`ciw`、`u`、visual mode。
- 不追求完整的 Vim 兼容。覆盖 90% 微操作的大概是二三十个 motion 和 operator。

### 1.3 和 agent 共享同一份工作状态

这是它比"终端里再开一个 Neovim"强的地方，本质是人和 agent 的协作编辑协议，Vim 只是一种输入方式。

- 人在 agent 改过的文件里手动改了一行，agent 应该立刻知道（"Human edited session.ts:43 after my last patch"），之后把人的改动当作最新事实，不拿自己的旧补丁覆盖回去。
- 反过来，人在看文件时 agent 改了别处，界面标出"● modified by agent"。

### 1.4 一个很小的原语：`open(resource, view)`

不把编辑器做成一个大模块。

- resource：文件、diff、终端、浏览器、图片、Markdown、测试结果、agent 的执行轨迹。
- view：决定怎么呈现。
- 键位：`Enter` 查看、`e` 编辑、`d` diff、`b` 浏览器、`t` 终端、`Esc` 返回。

整个界面是一棵可以逐层进入的树（任务 → 文件 / 测试 / 浏览器 / agent 轨迹 → 具体视图），而不是"左边文件树、中间编辑器、下面终端、右边聊天"那种把 VS Code 压进终端的布局。

### 1.5 Vim 的语法作用于整个工作台

- 通用导航：`j/k`、`gg/G`、`/` 搜索任何资源、`Enter` 进入、`Esc` 返回、`Tab` 切任务、`gd` 跳到定义、`gr` 引用、`]c/[c` 上下一处改动、`]e/[e` 上下一个错误、`]a/[a` 上下一个 agent 动作、`za` 展开或收起。
- 工作台的 operator：`da` 驳回一个 agent 动作、`aa` 接受、`ra` 要求修改。

这样 Vim Mode 不是"内置了一个简陋版 Vim"，而是整个工作台采用一套可组合的键盘语法。

### 1.6 不逼所有人学 Vim

底层是"动作、导航、键位表"三层，不是 Vim。同一个动作（`workspace.open`、`workspace.back`、`file.edit`、`file.save`、`change.next`、`change.accept`、`change.reject`、`agent.interrupt`、`browser.open` 等）可以映射成 Vim、Emacs、默认或自定义的键位。鼠标用户照样点。

### 1.7 外部编辑器是一等公民

- `e` 进内置的轻量编辑器。
- `E` 把当前文件和行列号交给用户自己的编辑器（`$EDITOR` / `$VISUAL`：nvim、hx、vim、code、zed）。编辑完回来，agent 自动感知 diff。
- 80% 的修改不用离开 MMP，20% 的重编辑不去重新发明 Neovim。

## 2. 主控的看法（建议，没有拍板）

认同：目标的定义；外部编辑器逃生口；`open(resource, view)` 这个原语（现在的 `/preview` 就是它的第一个实例：资源是文件，视图是查看）。

会调整的：

| 点 | 看法 |
|---|---|
| 先后 | 先做"人改了什么，agent 要知道"，再做内置编辑器。这个协议对外部编辑器同样成立，而且只用 Pi 的扩展接口就能做 |
| 内置编辑器的范围 | 要卡死。撤销、搜索、多字节字符、换行这些基础必须做对。pi-tui 自带的多行编辑器已有撤销和单词移动，可以作起点 |
| 整个工作台用 Vim 语法 | 先不做。它要求界面先有统一的"可选中对象"模型，现在的对话区还不是这种结构。等有两三个视图后再抽 |
| 键位表 | MMP 已经用 Pi 的键位表、可以配置。新视图的键应该登记进同一张表；现在 `/preview` 的键是写死的，这是它的一个欠缺 |

建议的顺序：

1. `E`：把文件和行号交给 `$EDITOR`，回来后把 diff 告诉 agent。
2. `/preview` 加 diff 视图和"本次任务改动的文件"入口。
3. 轻量 Edit 视图，带一小组 Vim 键位。
4. 有了三个视图之后，再抽 `open(resource, view)` 和统一的导航语法。

## 3. 用户随后的决定（2026-10-04）

先不支持编辑，先把预览体验做到最好。预览功能的设计另行讨论。
