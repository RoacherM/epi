- **预期 + 风险**：**预期每两轮节省 35–45 分钟**（直接砍掉 `0.1.24-r1` 的 21.43m 和 `0.1.24-r2` 的 23.15m，彻底根除 `preview.test.mjs` 在子代理后台挂死导致盲睡 10 分钟的事故）；**风险**：主控本地环境与干净副本不一致，通过预检脚本本身就在 `git archive` 出来的 `/tmp/epi-review-<id>/repo` 禁网沙箱中运行来消除。**改完怎么知道有效**：检查审查子代理 JSONL 中不再出现 `node --test test/*.test.mjs` 和 `eslint`，工具 `durationMs` 总和 ≤ 60 秒。

### 改动 3：第 2 轮及之后的修复复查改为「严格增量复查」，禁止重扫未改代码与无界 Fuzzing（杠杆 #3）

- **删什么**：删掉 `docs/dev-workflow.md` 第 2 节「审查—修复循环」中未限制范围的「专门找绕过」及 `pack-2.md` 让子代理当作半全量终审重读全部关联文件的做法。
- **改成什么**：第 2+ 轮复查（`pack-2.md` / `review-2.md`）实行**严格增量预算（墙钟 ≤ 10 分钟，轮次 ≤ 25 轮，输出 ≤ 20k token）**，动作只限三步：① 在新副本上重跑上一轮失败的复现脚本确认全过；② 将本轮新增回归测试放到 `before/` 副本确认修复前失败；③ 只读 `git show <fix-commit>` 改动的函数，针对每条 P0–P2 修复最多写 1 个绕过探针（单探针运行 ≤ 3 秒），拿到结果立即写 `review-2.md` 退出。
- **改在哪**：`docs/dev-workflow.md` 第 2 节「审查—修复循环」第 3 点；`docs/dev-workflow-herdr.md` 第 3.1 节 N6「修完主控再打一个小的补充包复查」。
- **预期 + 风险**：**预期每轮复查节省 20–30 分钟**（将 `0.1.24-r2` 的 57.80 分钟压到 ≤ 10 分钟；注意 `0.1.24-r2` 在前 35 分钟已找到 `p1-bypass` 和 `json-offset-cost` 两个真问题，若去掉重复读文件与全量测试，10 分钟内即可交付）；**风险**：修复可能破坏未改文件的远端调用者，靠预检脚本已跑过的全量测试兜底。**改完怎么知道有效**：第 2 轮复查会话轮次 ≤ 25 轮、墙钟 ≤ 10 分钟。

### 改动 4：限制单次送审规模（按独立特性拆审 ≤ 800 行源码 diff）并冻结被审分支（杠杆 #4）

- **删什么**：删掉主控把多个互不相关的功能攒成一个超大 `integrate/*` 分支（如 0.1.24 把 `epi:web` 和 `tui-glyphs` 共 52 文件/+3,205 行合包）一次性送 G5/N6 审查，以及在审查运行中途往被审分支追加 commit（如 `422032f`）的做法。
- **改成什么**：① **单次审查规模上限**：`src/` 新增+修改超过 800 行或包含两个独立功能时，必须按功能在各自合入前分别走 G5 审查，大节点 N6 只审跨功能交互（若两个功能无共享模块则免除重复终审）；② **被审提交不可变**：`pack.md` 写定被审 commit SHA 后，审查子代理运行期间主控不得修改该分支引用（主控自己发现的补充修复记入下一轮同修）。
- **改在哪**：`docs/dev-workflow-herdr.md` 第 3.1 节 N3/N6、第 3.2 节 `pack.md`、第 3.3 节 G5。
- **预期 + 风险**：**预期节省 20–30 分钟**（避免 3,200 行大包导致上下文与思考复杂度指数级膨胀，并消除中途改 HEAD 导致子代理花 ~6 分钟重打副本重跑）；**风险**：拆成两个小包会有两次启动开销（每次 < 30 秒），远小于巨型包带来的非线性思考膨胀。**改完怎么知道有效**：每份 `pack.md` 对应的 `git diff --stat -- src` 改动行数 ≤ 800 行，且审查期间被审分支 SHA 不变。

### 改动 5：P3 发现免写复现脚本、不触发独立复审轮次（杠杆 #5）

- **删什么**：删掉 `docs/dev-workflow.md` 第 2 节「审查者每条发现都要复现：把复现脚本写进 scratchpad」对 P3 的无差别要求，以及 `pack-2.md` 要求审查子代理逐条复核 P3-1..P3-11 的规定。
- **改成什么**：**只有 P0–P2（阻塞合并项）强制要求编写可执行复现脚本并标 CONFIRMED**；P3（文案、边界小瑕疵、导出/复杂度整洁项）只需给出精确的 `文件:行号` 与静态推导（标 PLAUSIBLE 或附一行 `rg` 命令），**禁止为 P3 编写独立 `.mjs` 探针脚本**；且 P3 修复后由主控自验，不放入 `pack-2.md` 让审查子代理复核（若首轮无 P0–P2、只有 P3，结论直接判「可接受」，主控修完 P3 即可合并，不跑第 2 轮）。
- **改在哪**：`docs/dev-workflow.md` 第 2 节「审查—修复循环」第 1、3 点；`docs/dev-workflow-herdr.md` 第 3.1 节 N3/N6 及第 3.2 节 `review-N.md`。
- **预期 + 风险**：**预期每两轮节省 15–20 分钟**（`0.1.24-r1` 的 12 条发现中有 10 条是 P3，为其编写 `mcp-truncate.mjs`、`no-source-call.mjs`、`later-new.test.mjs`、`dates-probe.mjs`、`trace-spin.mjs` 及在 r2 逐条复核耗费约 18 分钟）；**风险**：真 P2 被误标成 P3 放过，靠明确 P1/P2 定义（硬规则、数据/安全、可见行为与渲染契约错误一律 ≥ P2）约束。**改完怎么知道有效**：`review-N.md` 中所有复现脚本 `.mjs` 100% 对应 P0–P2，P3 零脚本，且无「仅因 P3 开启下一轮审查」的记录。

## 5. 不能动的护栏

以下 6 条护栏在 `0.1.23` 和 `0.1.24` 中被实证证明抓到了全量测试（1235/1235、1287/1287）完全漏掉的真实 P1/P2 缺陷，**绝对不能删**：

1. **闸门 G5（作者不自审）与合并前强制审查（`dev-workflow-herdr.md` §3.3 G5、`dev-workflow.md` §2）**：
   - **为什么不能动**：`0.1.23` 和 `0.1.24` 的代码均为主控本人编写，主控自测全量测试 100% 通过后送审，独立审查子代理仍在 `0.1.23` 抓出 **6 条 P2**（折叠计时起点错、tip 外耗时条每帧重绘、误截 `✗ ` 普通输出、4 空格伪闭合围栏、跨边界块重绘、`updateArgs` 缓存不失效），在 `0.1.24` 抓出 **1 条 P1 + 1 条 P2 + 2 条 r2 绕过**（API key 经非法 header / 损坏 JSON / Exa 内容回显泄露、Ctrl+O 展开后 `shownAt=undefined` 触发每帧整屏重绘、8KB 损坏 JSON 二次方卡顿）。去掉 G5 会让这些硬规则违约和渲染回归直接合入 `main`。
2. **P0–P2 必须 CONFIRMED 且附可执行复现脚本，退回修复必须重跑原复现脚本（`dev-workflow.md` §2）**：
   - **为什么不能动**：`0.1.23-r2` 和 `0.1.24-r2` 都是靠重跑上一轮探针 + 写绕过探针，抓到了「第 1 轮修法不完整或引入新回归」（如 `0.1.23-r2` 抓到整块缓存弄坏 `updateArgs`、`0.1.24-r2` 抓到 Exa 返回内容回显 key）。如果允许只靠嘴说 PLAUSIBLE 而不跑脚本，审查会退化成无效的文字臆测。
3. **新测试「修复前失败、修复后通过」+ 至少 2 个故意改坏（变异）检查（`dev-workflow-herdr.md` §1、§3.1 清单第 2/6 条）**：
   - **为什么不能动**：防止测试被重绘、缓存或宽松断言碰巧满足（如 `0.1.23-r1` 发现原测试靠手动预置 `startedAt` 和只把工具放 tip 内而假性通过）。
4. **临时副本隔离（`git archive` 到 `/tmp`）与禁网/临时 `HOME` 沙箱，严禁 `git stash`（`dev-workflow-herdr.md` §1、§3.1，`dev-workflow.md` §2、§3.5）**：
   - **为什么不能动**：所有 worktree 共用一个 git stash 栈，并行时 `git stash` 会互相弹出或污染工作树（历史事故 U5 × D63）；修复前副本可能缺少离线开关而真实访问外网（D63 曾真实请求 npm registry）或污染用户的 `~/.epi` 与真实剪贴板。
5. **硬规则一票否决（`dev-workflow.md` §5、`dev-workflow-herdr.md` §1）**：
   - **为什么不能动**：配置隔离（不读 `~/.pi`、项目 `.pi/`、`PI_*`）、项目配置先信任后读取、不泄露密钥、失败可见不静默兜底、对外只暴露 `epi`。这是 Epi 的核心契约（例如 `0.1.24-r1` 的 P1-1 密钥进 tool result 和会话文件，一旦放过就会把用户真实 API key 永久写进明文日志并传给模型服务商）。
6. **模型可见内容快照比对（`code-quality.md` §3 `model-snapshot.mjs --diff`）**：
   - **为什么不能动**：防止代码改动在不知情下改变发给模型的 system prompt 或 tool schema，破坏缓存命中率与 benchmark 基线。
